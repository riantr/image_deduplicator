# 2026-11-11 续：特征计算阶段优化

## 背景
承接同日「代理哈希预筛」那一轮。预筛把比对阶段从 199s 降到 1.8s 后，
瓶颈转移到**特征计算**阶段。

## 一、先剖析，确认瓶颈已转移

`--profile` 输出（360 张图）：
```
Sift  特征 2,707ms  比对 519ms
Surf  特征 1,138ms  比对 258ms
特征总计 6,504ms  vs  比对总计 1,109ms
```
SIFT + ORB 占特征开销的 59%。

## 二、分阶段剖析（新增 --stage 工具）

单线程、60 张 400×300 图：
```
Cv2.ImRead 解码        2.97ms/张
  含 CvtColor 灰度      0.30ms/张
  含代理哈希+亮度        0.35ms/张
SIFT 特征             17.68ms/张   ← 热点
ORB 特征               7.43ms/张
HOG(Lance 基)          12.75ms/张
```
解码只占 2.97ms，而 SIFT 要 17.68ms —— 瓶颈明确在特征检测本身。

## 三、发现并移除无效的「放大」逻辑

原 ORB 实现会把小图**放大**到 480 再提取特征，注释理由是「ORB 对尺度敏感」。

实测打脸：
| 工作尺寸 | SIFT | ORB |
|---|---|---|
| 256 | 8.90ms | 4.00ms |
| 320 | 9.82ms | 5.52ms |
| 400（原始）| 17.68ms | 7.43ms |
| 480 | 30.15ms | 10.62ms |

**放大到 480 比保持原尺寸还慢**（10.62 vs 7.43），纯属浪费。
真正有效的是**限制上限**，而不是提升下限。

## 四、关键决策依据：质量验证（新增 --quality 工具）

不能为了速度牺牲准确度。写工具验证不同工作尺寸下的相似度质量：

| 工作尺寸 | 重复对(g0) | 重复对(g5) | 独立(u0/u1) | 独立(u0/u2) |
|---|---|---|---|---|
| 原始 | 1.0000 | 1.0000 | 0.0000 | 0.0000 |
| 400 | 1.0000 | 1.0000 | 0.0000 | 0.0000 |
| 320 | 1.0000 | 1.0000 | 0.0000 | 0.0000 |
| 256 | 1.0000 | 1.0000 | 0.0000 | 0.0000 |
| 192 | 1.0000 | 1.0000 | 0.0000 | 0.0000 |

**缩小到 256 后质量完全无变化** —— 重复对仍是 1.0，独立图仍是 0.0。
这才有底气把上限设为 256。

## 五、其他改动
- 代理特征先缩到 64×64 再算：0.42 → 0.33ms/张
- `ComputeLumaStats` 检测到输入已是 64×64 时跳过二次缩放

## 六、结果
| 阶段 | 优化前 | 优化后 |
|---|---|---|
| SIFT 特征 | 17.68ms | **8.27ms** |
| ORB 特征 | 7.43ms | 8.68ms（含新放宽的重试路径） |
| 代理哈希 | 0.42ms | 0.33ms |

103 项断言全通过，0 错误 0 警告，检出组数不变（60/61/60）。

## 七、经验
1. **每轮优化前先重新剖析**。上一轮优化完比对，这轮瓶颈就转移了。
   沿用旧结论会浪费时间。
2. **注释里的理由要验证**。「ORB 对尺度敏感所以放大」是前人写的，
   实测证明对 400×300 的输入毫无收益，甚至有害。
3. **性能优化必须有质量验证配套**。--quality 工具是本轮最有价值的产出——
   它把「能不能缩小」这个决策从直觉变成可验证的结论。
4. **单线程 vs 并行的测量差异**：profile（并行）下 SIFT 看起来变慢了，
   但 --stage（单线程）显示从 17.68 降到 8.27ms。
   OpenCV 内部已有多线程，外层再 `Parallel.For` 会产生线程竞争，
   **两者要分开测量才能看清真实收益**。
