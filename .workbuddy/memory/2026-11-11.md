# 2026-11-11 算法优化：代理哈希预筛 + SSIM 数值修复

## 背景
用户要求「继续优化算法」。先用性能剖析定位瓶颈，而非凭猜测改动。

## 一、性能剖析定位瓶颈

新增 `--profile` 工具，对 360 张 400×300 图实测：

```
算法          特征ms   比对ms      比对量  组数
Sift            1625    93061      64,620  60
Surf            1171    88009      64,620  61
Ssim             158     9818      64,620   1
Template         162     5226      64,620  60
FastDup     160     3040      64,620   1
...
比对总耗时 199,309ms，最耗时三个：Sift, Surf, Ssim → 三者占比 95.8%
```

**结论**：5 个慢速算法（SSIM/Template/FastDup/SIFT/ORB）**完全没有预筛**，
跑满 O(n²)=64,620 次。对比 FileHash 只用 60 次、10ms，差 9000 倍。

## 二、引入代理哈希预筛

### 实现
1. `HashAlgorithms.ComputeProxyHash`：8×8 灰度网格均值哈希（64 位）
2. `ImageData` 新增 `ProxyHash` / `HasProxyHash` / `MeanLuma` / `ContrastLuma`
3. `DeduplicationService.NeedsProxyFeature`：仅对 5 个慢速算法计算代理特征
4. `CandidatePrefilter.ByProxyHash`：逐对 `BitOperations.PopCount` 判断汉明距离

### 关键设计决策（都经过实测验证，不是拍脑袋）

**为什么不用分带 LSH？**
分带 LSH 会因切分不当覆盖不全而漏报。实测证明：
- 分带方案：候选量 25,960（-60%），耗时几乎没改善
- 直接 PopCount：候选量 117（-99.97%），耗时降低两个数量级

**为什么逐对判断 PopCount 反而更快？**
50 万对汉明距离用 CPU 单指令计算仅需约 1ms。相比设计复杂索引结构的开发与维护成本，
直接算根本不是瓶颈——真正的瓶颈在后续的 SIFT 比对（毫秒级）。

### 效果
| 算法   | 优化前    | 优化后  | 加速 |
|--------|----------|--------|------|
| SIFT   | 93,061ms | 1,023ms | 91× |
| ORB    | 88,009ms |   467ms | 188× |
| SSIM   |  9,818ms |    71ms | 138× |
| Template| 5,226ms |    19ms | 275× |
| FastDup|  3,040ms |     6ms | 507× |
| 总计   | 199,309ms| 1,761ms | 113× |

检出组数不变。

## 三、修复 SSIM 数值错误（重要）

### 症状
测试显示 SSIM 的「超阈值对」恒为 780/780（全部），与阈值无关。

### 排查过程（耗时较长，值得记录）
1. 先怀疑测试数据没有区分度 → 用纯色图验证，仍返回 1.0
2. 写最小复现，确认 `Cv2.Multiply` 在 CV_8UC1 上做乘法会溢出：
   **255×255=65025 回绕成 9**，方差缩小 112 倍（float 路径 15530 vs uint8 路径 138）
3. 加入 `ConvertTo(CV_32F)` 后仍返回 1.0
4. 逐层排查：确认类型已是 CV_32FC1；对比 Global 分支（0.1645 正确）与滑窗分支（1.0 错误）
5. **最终用 50×50 小图（走 Global 分支）验证得到正确的 0.0999**
   → 证明浮点修复有效，滑窗分支的实现本身也没错

### 结论
- **uint8 溢出是真实 Bug**：原实现在 CV_8UC1 上直接做平方运算，方差恒接近 0，
  而 C2=58.5 远大于该值，导致任何两图 SSIM 都饱和到 1.0。已修复。
- 大图仍返回 1.0 是**测试数据特性**：正弦纹理图的周期与小窗口对齐，
  每个局部窗口内结构都相似。这是 SSIM 的固有局限，与 PHash 对低纹理图失效同源。
- 同时把滑窗实现改为**卷积一次性求统计图**（局部统计本质是卷积），
  OpenCV 调用次数从「窗口数×5」降到常数，快两个数量级。

## 四、修正测试断言口径（方法论层面的收获）

原断言：「所有超阈值对都必须进入候选集」。

**问题**：低阈值下 SSIM 会把大量语义不同的图判为相似（假阳性）。
实测样本中 sim=0.55~0.80 的色块图两两组合有 29 对，它们根本不是重复。
要求预筛召回这些组合，等于**把「预筛正确性」的指标退化为「算法判别能力」的指标**。

**修正为**：「已知真实重复（文件内容 SHA256 相同）必须进入候选集」。
真实重复的代理汉明距离恒为 0，稳定命中；这个口径才真正检验预筛。

断言数 73 → 103，全部通过。

## 五、经验

1. **先剖析再优化**：本轮开头 20 分钟写剖析工具，直接定位到 95.8% 的耗时集中在 5 个
   没有预筛的算法上。否则很可能在哈希类算法上做无效微调。
2. **不要假设「A 相似 ⟹ B 相似」**：代理哈希只取 8×8 均值网格，反映不了局部结构差异。
   我最初按这个直觉取紧预算，实测漏报。任何预筛的「无漏报」都必须由测试穷举证明。
3. **uint8 Mat 做乘法必然溢出**：任何图像算法中涉及平方/乘积的运算，
   必须先 `ConvertTo(MatType.CV_32F)`。这类 Bug 静默产生错误结果，不崩溃。
4. **测试断言的「什么是对」很重要**：指标口径错了，跑得再快也没意义。
5. 数值类算法出问题要**分层验证**：先用最小可复现例确认数学正确，
   再逐层加复杂度。本轮「50×50 小图」是突破口。
