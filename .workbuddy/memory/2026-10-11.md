## 一、发现并修复的数据丢失缺陷（本轮核心）

审查 `RecycleBinService` / `FileOperationService` / `MainViewModel` 删除链路，
通过编写测试**复现**出真实的数据丢失场景：

### 1. MoveFile 双重改名 → 恢复时文件丢失（严重）
`MoveFile` 内部会调 `HandleFileNameConflict` 二次改名，但 `MoveToRecycleBin`
已经算过一次路径并据此写 `.meta`。两次改名导致 meta 记录的路径与实际落盘路径错位，
恢复时找不到文件。
**修复**：`MoveFile` 不再自动改名，目标已存在即返回 false，由调用方显式处理冲突。
调用方拿到的返回值与实际落盘路径始终一致。

### 2. 撤回删除记录了错误的路径（严重）
```csharp
duplicate.Path = recyclePath;                              // 先改写
_deletedItemsHistory.Push(new DeletedItemInfo(duplicate.Path, ...));  // 再入栈
```
顺序颠倒导致 `FilePath` 存的是回收站路径，撤回时文件被"还原"到回收站自己身上。
**修复**：先记录原路径再改写；撤回时同时把 `DuplicateItem.Path` 还原为原路径。

### 3. SwapImages 回滚不完整
步骤2 成功、步骤3 失败时，回滚条件 `!File.Exists(originalPath)` 为 false，
文件卡在 .tmp 且原路径被占用。
**修复**：改为三步移动 + 每步完整回滚；临时文件用 GUID 命名并置于同目录（保证同盘原子重命名）。

### 4. RecycleBinService 其他加固
- 移动失败时清理已写的 meta（改为先移动后写 meta，写 meta 失败不影响文件安全）
- 恢复时校验 meta 内容非空、原目录不存在则自动创建
- meta 读取后 `.Trim()`，避免尾部换行导致路径无效

## 二、Histogram 预筛漏报（被新测试抓出）

上轮用随机噪声图测不出问题，换纹理图后暴露：**峰值分桶预筛漏报 104 对**。

修复过程（三次迭代）：
1. 加邻域扩展 → 漏报 69 对（峰值相近但量化格位不同）
2. 改分段键 + 邻域展开 → 漏报 0，但**收益归零**（候选 = 全量）
3. 最终方案：**均值排序 + 二分滑窗剪枝** → 漏报 0 且削减 9.9%

关键认识：直方图相似度是全维皮尔逊相关，**没有哈希分带那样严格的局部等价关系**，
任何基于峰值/分段键的启发式分桶都无法保证召回。只有均值差界可证明。

## 五、经验

1. **文件操作类代码必须写测试**。这几处缺陷逻辑上看起来完全正确，
   只有真正执行「删除→占用→恢复」才会暴露。
2. **预筛的「无漏报」需要穷举证明**，不能靠抽样测试。测试里要对每个算法
   暴力算出全部超阈值对，逐个确认包含在候选集中。
3. 测试数据要覆盖**算法边界**：低纹理图、多频纹理图、纯色图、极小图。
4. 修复时区分「代码错」和「测试错」——本轮有 2 次是测试断言写错而非代码有问题
   （Diag3 证明代码行为正确，是断言没考虑改名恢复）。
